主要阐述说明了自己的学习过程，因为自己的问题还没弄好

背景

​ 在使用NVIDIA Jetson Nano Developer Kit开发过程中，想对gpio12进行pwm输出，在不知道gpio12的配置的时候，并且我不知道Linux内核版本的情况下，反汇编得到了起始的设备树dts文件。后来，我得知在nvida ////sudo /opt/nvidia/jetson-io/jetson-io.py下可进行图形化配置，在论坛得知可以通过**配置工具 (jetson-io)**进行配置。我的猜想是它会重新编译在/boot/下的设备树，可是反汇编后发现并没有改变，和原来反汇编的结果是一样的。

研究过程

​ 查阅资料发现，在配置使用jetson-io的情况下，并不会改变原始的设备树文件，而是通过生成一个或者多个增量式的配置文件，即设备树插件（Device Tree Overlay，文件后缀为.dtbo）

会产生类似这种dtbo文件。

那么让我们学习dtbo

DTBO（Device Tree Blob Overlay）在Linux中的作用是作为一种“增量补丁”，让你在不修改、不重新编译主设备树（DTB）的情况下，动态地添加、修改或禁用硬件配置信息。

作用：

  1. 硬件原型开发与调试：方便调试，在调试硬件的时候，这种方式可以不用重新编译dtb文件再上电，更不用编译整个内核，通过dtbo插件，快速添加或者修改硬件插件，方便Linux驱动开发者与硬件进行适配调试。
  2. 厂商驱动解耦：在Soc厂商核心提供的芯片设备树，和自己添加的特殊设备树进行解耦，方便双方独立更新。

🔹 /dts-v1/; —— 设备树版本声明

  • 作用：指定该源文件遵循的设备树语法版本。目前广泛使用的就是 v1 版本。
  • 必要性：几乎所有现代设备树源文件的开头都包含这行，它告诉 DTC 使用新版语法规则进行解析（早期版本是 v0，现已淘汰）。
  • 位置：必须出现在文件的最前面（注释之后）。

🔹 /plugin/; —— 叠加层标识

  • 作用：声明该文件是一个设备树叠加层（Device Tree Overlay），而不是一个完整的、独立的设备树。
  • 意义：当 DTC 看到这个标记时，它会以叠加模式编译源文件：
    • 允许使用 引用外部节点（如 &i2c1）而不需要这些节点在当前文件中定义。
    • 自动为生成的二进制文件（.dtbo）生成必要的 符号信息（相当于隐含了 -@ 编译选项），以便后续可以动态地叠加到基础设备树上。
    • 源文件中必须包含 /plugin/; 才能正确使用叠加层语法（如 &{/} 向根节点添加内容）。
  • 注意：叠加层源文件通常也包含 /dts-v1/;，两者共同表明这是一个 v1 版本的设备树叠加层。

简单来说：不是 “不想”，而是你的 ATK-IMX6U 开发板内核环境不满足动态加载的核心条件，强行尝试只会浪费时间。

结果

为什么无法动态加载？（核心原因拆解）

动态加载 dtbo 必须同时满足 3 个条件，你的环境只满足 1 个，另外 2 个核心条件缺失：

条件 你的环境状态 是否满足 补充说明
1. 内核开启 CONFIG_OF_OVERLAY=y 是（zcat /proc/config.gz 验证过） ✅ 仅配置层面开启，无实际功能支撑
2. 内核开启 CONFIG_CONFIGFS_FS=y 且初始化 device-tree 目录 否（/sys/kernel/config 为空） ❌ 内核未创建 Overlay 所需的核心目录
3. 存在 of_overlay 内核模块 / 内置逻辑 否（modprobe of_overlay 提示模块不存在） ❌ 核心功能模块缺失，无法解析 dtbo

👉 本质：你的内核是 “阉割版”—— 仅在配置文件中标注了 CONFIG_OF_OVERLAY=y，但实际编译时并未将 Overlay 核心逻辑 / 模块内置到内核，属于典型的 “配置和实际编译不一致”（IMX6ULL 原厂内核常见问题）。

:( 提供了另外一种思路就是通过fdtoverlay（即下载dtc下的工具），暂且不做说明。
